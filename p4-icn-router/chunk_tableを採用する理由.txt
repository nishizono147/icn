chunk_table（push 型）を採用する理由
（2026-10-17 作成）

================================================================
■ 2 つの方式
================================================================

・chunk_table（push 型）: Consumer は Interest を 1 本送る。
  キャッシュを持つスイッチ（または Producer）が全チャンクを返す。
  スイッチはキャッシュから返すとき、Interest のコピーをスイッチの中で一周（clone + recirculate）させながら
  チャンクを 1 つずつ作る。
・chunk_pull（pull 型）: Consumer は chunk 0 の Interest を送り、Data の total_chunks で全チャンク数を知ったら、
  残りのチャンクの Interest をまとめて送る。スイッチは Interest 1 本に Data を 1 つ返す。

================================================================
■ 理由 1：キャッシュが遠い場合に速い
================================================================

計測結果（取得時間 ms、各 20 セッションの平均。results/compare_chunk_methods_raw.csv、
compare_chunk_methods_c10_raw.csv、compare_chunk_methods_c10_run2_raw.csv、my_c10_raw.csv）

  | 返す場所       | 4 チャンク table / pull | 10 チャンク table / pull |
  |----------------|-------------------------|--------------------------|
  | h2（Producer） | 5.0 / 8.2               | 7.1 / 12.9               |
  | s3             | 5.4 / 7.3               | 9.3 / 11.5               |
  | s2             | 4.4 / 5.1               | 8.2 / 9.1                |
  | s1             | 2.8 / 2.7               | 6.6 / 5.8                |

・Consumer のすぐ隣（s1）以外では、すべて chunk_table の方が速い
・pull 型は、最初のチャンクを受け取ってからでないと残りを要求できないので往復が 2 回必要。
  push 型は 1 回で済む。返す場所が遠いほど往復 1 回の時間が大きいので、差が大きくなる
・逆転する s1 でも、差は 0.2〜0.8 ms

s1 で逆転する理由:
  pull − table ≒ 往復 1 回分（距離で変わる）−（push 型がスイッチの中で一周させる分の余計な時間：場所によらず一定）
  返す場所が近いほど往復 1 回分が小さくなり、s1 で一定の部分を下回る。
  チャンク数が多いほど一定の部分が大きくなるので、10 チャンクの方が s1 での逆転の幅が大きい。

================================================================
■ 理由 2：実際のネットワークでは、push 型の有利な範囲がさらに広がる（推論）
================================================================

・s1 で pull 型が速くなるのは、BMv2 では一周（recirculate）の処理が重いため
・実機のスイッチのチップでは、一周にかかる時間はごく短い
・実際のネットワークでは、スイッチどうしの距離があるので、往復 1 回の時間の方がずっと大きい
→ 往復が 1 回少ない push 型が有利な範囲は、BMv2 の結果より広がると考えられる

注意: 測定で確かめたものではない。論文では「考えられる」と書く。
      Mininet のリンクに遅延（リンクごとに数 ms）を加えた計測で確かめると根拠が強くなる。

================================================================
■ 理由 3：Interest が少ない
================================================================

  |                                   | chunk_table                | chunk_pull                       |
  |-----------------------------------|----------------------------|----------------------------------|
  | 1 つのコンテンツに送る Interest    | 1 本                       | チャンクの数だけ                 |
  | 途中のスイッチが処理する Interest | 1 本 × 通るスイッチの数    | チャンクの数 × 通るスイッチの数  |

チャンクの数が増えるほど、pull 型では途中のスイッチの負担と、上流へ流れる Interest が増える。
push 型は、コンテンツの大きさに関係なく Interest は 1 本。

================================================================
■ 理由 4：コンテンツ単位で管理できる
================================================================

・PIT: 1 つのコンテンツにつき 1 つの記録で済む（pull 型はチャンクごとに必要）
・MCD: コンテンツの全チャンクがまとめて 1 ホップずつ移動するので、チャンクが別々のスイッチに散らばらない
・off-path キャッシング（今後）: 「このコンテンツを持っている」という情報もコンテンツ単位で済む
→ register の大きさが限られるスイッチのチップでは、記録の数が少ないことが大きな利点

================================================================
■ 理由 5：Consumer が単純
================================================================

Consumer は Interest を 1 本送るだけでよく、全部で何チャンクあるかを先に知る必要もない。

================================================================
■ 理由 6：研究の流れとのつながり
================================================================

研究室で取り組んできた複数チャンクの実装（後輩の卒業研究、port 511 版）の問題
（BMv2 では port 511 が破棄用のポート）を特定し、clone + recirculate で修正して完成させた方式なので、
その成果を発展させる形で研究を進められる。

================================================================
■ 論文で合わせて書く弱点（制約）
================================================================

  | 弱点                                 | 内容                                                                     |
  |--------------------------------------|--------------------------------------------------------------------------|
  | 実機での帯域の消費                   | recirculate はチップの処理能力を使う。チャンクの数が多いと、             |
  |                                      | ほかのパケットの処理に使える分が減る                                     |
  | 失われたチャンクだけを要求し直せない | 失われたら、コンテンツ全体を要求し直すことになる                         |
  | 一度に全部返す                       | チャンクの数が多いと、スイッチの待ち行列（BMv2 の既定は 64 パケット）が  |
  |                                      | あふれる可能性がある                                                     |
  | Consumer のすぐ隣から返す場合         | BMv2 では pull 型の方がわずかに速い（0.2〜0.8 ms）                       |

================================================================
■ 論文向けの文の例
================================================================

  本研究では、1 つの Interest に対してスイッチがキャッシュから全チャンクを返す方式（push 型）を採用する。
  チャンクごとに Interest を送る方式（pull 型）と比較した結果、Consumer に隣接するスイッチから返す場合を除き、
  push 型の取得時間が短く、その差はチャンク数が多いほど大きかった。pull 型が速くなる場合も差は小さく、
  その原因は BMv2 における recirculate の処理の重さにあるため、往復遅延が大きい実際のネットワークでは
  push 型が有利な範囲はさらに広がると考えられる。また、push 型は Interest がコンテンツあたり 1 本で済み、
  PIT やキャッシュの管理をコンテンツ単位で行えるため、メモリの限られたデータプレーンに適している。
