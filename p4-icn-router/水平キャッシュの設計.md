# 水平キャッシュの設計

（2026-10-22 作成）

Consumer から Producer への経路から外れた、隣のスイッチのキャッシュも使えるようにする仕組み。
[設計メモ.txt](設計メモ.txt) の ECST を、chunk_table（Interest 1 本で全チャンクを返す方式）の上に作る。

## 1. 何ができるようになるか

```
                 s1
              ／    ＼
           s2          s3
         ／  ＼      ／  ＼
       s4     s5   s6     s7
       |      |    |
       A      B    P（Producer）
```

1. A がコンテンツ X を何度も要求すると、MCD で X のキャッシュが s6 → s3 → s1 → s2 → s4 と A の隣へ移る
2. B が X を要求する。B の Interest は FIB に従って s5 → s2 → s1 → s3 → s6 → P と進む
3. s4 は B の経路から外れているので、今の仕組みでは使われない
4. 水平キャッシュでは、s4 が「X を持っている」と隣の s2 に知らせておく。s2 は B の Interest を s4 へリダイレクトし、
   s4 から X を返せる（B から見て s5 → s2 → s4。Producer まで行かずに済む）

## 2. 用語

| 用語 | 意味 |
|---|---|
| LCST | 自分のキャッシュ（今の `content_cache` と `total_chunks_reg`） |
| ECST | 隣のスイッチが持っているコンテンツの記録。「コンテンツ X は、このポートの先の隣が持っている」 |
| FIB | Producer の方向を決める表（名前 → 出力ポート） |
| PIT | Interest が来たポートの記録。Data はここをたどって戻る |
| リダイレクト | ECST に従って、Interest を FIB とは別の隣のスイッチへ送ること |

## 3. 全体の動き

1. **通知**: スイッチは、LCST の行が変わったら（コンテンツをキャッシュした、消した）、そのコンテンツの状態
   （あり ／ なし）を隣のスイッチ全部に知らせる。知らせるのは 1 ホップ先まで
2. **ECST の更新**: 通知を受け取ったスイッチは、ECST に「X は、通知が届いたポートの先にある」と書く。「なし」なら消す
3. **Interest の処理**: Interest が来たら、LCST → ECST → FIB の順に見る
   - LCST にある → 自分が返す
   - ECST にある → そのポートの隣へリダイレクトする
   - どちらにもない → FIB に従って Producer の方へ送る
4. **リダイレクト先になかった場合**: 通知が届く前にキャッシュが消えていた、など。リダイレクト先でも同じく
   LCST → ECST → FIB の順に見るので、多くの場合 FIB で Producer の方へ送られる

ECST には隣のスイッチの番号ではなく、通知が届いたポートを記録する。そのポートへ送れば、持っている隣に届く。
IWP の番号から出力ポートを引く表（設計メモの NMT）は要らない。

## 4. 決まり

### 4.1 Interest が来た方向へはリダイレクトしない
ECST のポートが、Interest が来たポートと同じなら、リダイレクトしない（FIB に従う）。
その隣は、自分の LCST で外れたから Interest を送ってきたので、ECST の記録は古い。

### 4.2 「あり」は、全チャンクをキャッシュし終えてから知らせる
chunk_table ではチャンクが 1 個ずつ届き、スイッチは chunk 0 があるかどうかだけで「キャッシュにある」と判断する。
chunk 0 の時点で知らせると、残りのチャンクがないうちにリダイレクトされてきて、中身が 0 の Data を返してしまう。
そのため、最後のチャンク（`chunk_id + 1 == total_chunks`）をキャッシュしたときに「あり」を知らせる。

### 4.3 自分がリダイレクトした Interest が戻ってきたら、PIT を上書きしない
**問題**: 木構造では、s4 から Producer への道は必ず s2 を通る。s2 が s4 へリダイレクトし、s4 になかった場合、
Interest は FIB に従って s2 に戻ってくる。

```
B → s5 → s2 ──リダイレクト──▶ s4 ──（なし。FIB）──▶ s2 → s1 → s3 → s6 → P
```

PIT は 1 つのコンテンツにつき 1 つのポートしか記録できない。s2 の PIT には B の方向（s5 側）が書いてあるが、
戻ってきた Interest で s4 の方向に上書きされ、Data が B に戻らなくなる。

**対策**: Interest に「リダイレクトしたスイッチの番号」を入れる。スイッチは、自分の番号が入った Interest が
戻ってきたら、PIT を書き換えずに転送する。ECST のその記録は古いので消す。

### 4.4 MCD との関係
- 今の MCD の決まりはそのまま使う。Data を受け取って `flag == 1` ならキャッシュし、`flag = 0` にして下流へ流す。
  エッジ（Consumer から直接 Interest を受け取ったスイッチ。Interest の `flag == 1`）以外は、キャッシュから返したら消す
- リダイレクトされた Interest は `flag == 0` なので、リダイレクト先（例: A の隣の s4）は返したあとにキャッシュを消す。
  Data は `flag = 1` で s2 へ戻るので、s2 がキャッシュする。キャッシュはネットワークからなくならず、1 ホップ手前（s2）へ移る
- エッジが Consumer に返したときに消さないのは、消すとネットワークからコンテンツがなくなるため。
  リダイレクトの場合は 1 ホップ手前に残るので、消してよい

## 5. パケットの形

### 5.1 Interest（EtherType `0x88B5`）に足す欄

| 欄 | 大きさ | 中身 |
|---|---|---|
| `redirect_by` | 8 bit | リダイレクトしたスイッチの番号（`source_switch` と同じ付け方。0 = リダイレクトされていない） |

### 5.2 通知（新しい EtherType `0x88B7`）

| 欄 | 大きさ | 中身 |
|---|---|---|
| `content_id` | 32 bit | どのコンテンツか（名前を入れるときは名前の欄に置き換える） |
| `state` | 8 bit | 1 = あり、0 = なし |
| `sender` | 8 bit | 知らせたスイッチの番号（確認用。ECST にはポートを記録するので転送には使わない） |

Data（`0x88B6`）は変えない。

## 6. スイッチのデータ構造

今の chunk_table の register（`content_cache`、`total_chunks_reg`、`pit_table`、`switch_id_reg`）に、次を足す。

| register | 大きさ | インデックス | 中身 |
|---|---|---|---|
| `ecst_port` | `bit<9>` × 1024 | `content_id` | そのコンテンツを持っている隣へのポート（0 = なし） |

コンテンツ名を入れるまでは、今と同じく content_id をそのまま register の番号に使う。

コントローラが書き込むもの（`*-runtime.json`）:

| もの | 内容 |
|---|---|
| FIB | 名前（今は content_id）→ Producer の方向のポート |
| マルチキャストのグループ | 通知を送るポートの一覧（隣のスイッチがつながったポートだけ。ホストのポートは入れない） |

## 7. 処理の流れ

### Interest を受け取ったとき

```
if redirect_by == 自分:                       // 自分がリダイレクトした Interest が戻ってきた（4.3）
    PIT は書き換えない
    ecst_port[X] = 0                          // 古い記録を消す
    redirect_by = 0
    FIB に従って送る
    終わり

pit_table[X] = 来たポート
if LCST に X がある（chunk 0 が 0 でない）:
    キャッシュから全チャンクを返す（今の chunk_table と同じ）
    エッジでなければ（flag != 1）、返し終えたら消し、「X なし」を通知する
else if ecst_port[X] != 0 かつ ecst_port[X] != 来たポート:   // 4.1
    flag = 0、redirect_by = 自分
    ecst_port[X] へ送る（リダイレクト）
else:
    flag = 0
    FIB に従って送る
```

### Data を受け取ったとき（今と同じ ＋ 通知）

```
if flag == 1:
    キャッシュする、flag = 0
    最後のチャンクなら「X あり」を通知する       // 4.2
PIT に従って送る
```

### 通知を受け取ったとき

```
if state == あり:  ecst_port[X] = 届いたポート
else:               if ecst_port[X] == 届いたポート: ecst_port[X] = 0   // そのポートの記録だけ消す
通知は転送せずに捨てる（1 ホップ先まで）
```

## 8. 実装で必要なこと

1. **FIB を先に作る**: 今の Interest の転送は、送信元 MAC アドレスで次の行き先を決める表（`foward_interest`）を
   使っている。リダイレクトされた Interest は想定していない MAC アドレスで届くので、この表では転送できない。
   FIB（名前 → ポート）に置き換えてから、水平キャッシュを入れる（予定表の 2 のあと）
2. **通知のパケットの作り方**: P4 のスイッチは何もないところからパケットを作れないので、処理しているパケットの
   コピー（clone）を作り、通知に書き換えて送る（今の chunk_table で Interest のコピーを Data に書き換えているのと同じ仕組み）

   | 通知 | 元にするパケット |
   |---|---|
   | あり | キャッシュした最後のチャンクの Data |
   | なし | キャッシュから返し終えたとき（recirculate の最後の周）の Interest |

3. **通知の送り先**: マルチキャストのグループで、隣のスイッチ全部へ送る

## 9. 制約と今後

| 制約 | 内容 | 今後の対策の案 |
|---|---|---|
| 隣の 2 台が同じコンテンツを持つとき | ECST は 1 つのポートしか記録しないので、後から届いた通知で上書きされる。片方が「なし」を知らせると、もう片方が持っていても記録が消えることがある。MCD ではコピーが 1 つになりやすいので、起きにくい | ポートごとに 1 ビット持つ |
| 2 回以上のリダイレクト | 1 つの Interest が 2 回リダイレクトされると、`redirect_by` が 2 回目のスイッチの番号で上書きされ、最初のスイッチで PIT を上書きしてしまう。予定している木構造では、リダイレクト先が端のスイッチになり、来た方向へはリダイレクトしないので、ほぼ起きない | Interest ごとにちがう番号（nonce）を付け、PIT に記録して見分ける（NDN と同じ方法） |
| 通知が届くまでの間 | その間は ECST が古い。リダイレクト先で外れて FIB で送るので取得はできるが、遅くなる | - |
| 通知が失われたとき | ECST が古いまま残る（Mininet では起きにくい） | 一定時間ごとに通知し直す |
| PIT のポートは 1 つ | 複数の Consumer が同じコンテンツを同時に要求すると壊れる（今と同じ制約）。評価では順番に要求させる | PIT を複数のポートに対応させる |
| リダイレクト先で外れたとき | リダイレクト先の PIT に記録が残る（Data がそこを通らずに戻るため）。次の Interest で上書きされるので、実害はないと考える | - |
| キャッシュの行き来 | A と B が交互に要求すると、キャッシュが s2 と s4 の間を行き来し、毎回通知が出る | 評価で通知の数として数える |
| コンテンツ名 | 名前をハッシュにすると、ECST の場所もハッシュで決めることになり、LCST と同じく名札（ハッシュ全体）での照合が要る | 名前を入れるときに合わせて作る |
| 通知の範囲 | 1 ホップ先まで | 残りのホップ数の欄を足して広げる |

## 10. 評価の方法（案）

- **トポロジ**: 1 の木構造（A は s4、B は s5、Producer は s6 の下）
- **手順の例**: A が X を続けて要求し、キャッシュを s4 まで移す。そのあと B が X を要求する。
  A と B が交互に要求する場合も測る
- **比べる条件**: 水平キャッシュあり ／ なし
- **指標**: B の取得時間、返した場所までのホップ数、Producer まで届いた要求の割合、通知のパケットの数
