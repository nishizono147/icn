# 今後の研究の方針

最終更新: 2026-10-10

## 1. 研究の全体像

- **目的**: キャッシュ配置を工夫した ICN を普及させる
- **アプローチ**: ICN のルータ（IWP）を専用ハードウェアではなく P4 でソフトウェアとして実装する。
  独自プロトコルを扱え、キャッシュ配置の方式も柔軟に変えられるので、導入の壁が下がる
- **研究の中心**: キャッシュ配置の工夫。P4 やソフトウェアでの実装はそのための手段
- **NDN との関係**: 考え方と用語は NDN に揃え（Interest / Data、PIT、FIB、Content Store、階層の名前、
  セグメントごとの Interest）、パケットの形式は P4 で扱いやすい固定長にする。
  NDN の TLV 形式は可変長で P4 での解析が難しい（NDN.p4 も階層の数や長さに制限を設けている）ため

## 2. ここまでにできたこと

- コンテンツ ID + MCD による on-path キャッシュ（経路上に動的に配置）
  - MCD: 要求のたびにキャッシュが Consumer 側へ 1 ホップずつ移動する。
    Consumer 直近のスイッチ（エッジ）に来たらそこで保持する
- 複数パケット（チャンク）による大きいコンテンツの転送の基盤
  - `chunk_table`（Interest 1 本でスイッチが全チャンクを返す）:
    先行研究の port 511 の問題（BMv2 では破棄用のポート）を特定し、recirculate で修正して E2E で動作を確認
  - `chunk_pull`（チャンクごとに Interest を送る）:
    PIT をチャンクごとに分け、chunk 0 でチャンク数を知ったら残りの Interest をまとめて送る形にした
- 計測の基盤
  - 両方式で共通の Consumer（`consumer_bench.py`）
  - 方式を交互に回して計測するスクリプト（`run_compare_chunk_methods.py`）
  - Docker での再現可能な実行、スクリプトによるグラフの作成

### 今の実装（chunk_pull）と NDN の考え方の差

| 項目 | NDN | 今の実装 | 埋める段階 |
|---|---|---|---|
| Interest / Data、PIT をたどる Data | あり | あり | - |
| Content Store | あり | あり（register） | - |
| セグメントごとの Interest | あり | あり | - |
| 名前 | 階層のある名前 | 32 bit の数値 ID | (1) |
| FIB | 名前で転送先を決める | なし（送信元 MAC アドレスで経路を決め打ち） | (2) |
| PIT の集約（1 つの名前に複数のポート） | あり | なし（1 つの欄にポート 1 つ） | 基礎 |
| PIT の記録の期限 | あり | なし | 基礎 |
| 重複の検出（nonce） | あり | なし | 基礎 |

## 3. 決めたこと

### chunk_pull を今後の土台にする

計測結果（10 チャンク、取得時間 ms、各 20 セッションの平均。2 回計測して差は 0.4 ms 以内）:

| 返す場所 | chunk_table | chunk_pull（まとめて送る） |
|---|---|---|
| h2（1 回目） | **7.1** | 13.0 |
| s3（2 回目） | **9.3** | 11.5 |
| s2（3 回目） | **8.2** | 9.1 |
| s1（4 回目以降） | 6.5〜6.8 | **5.7〜5.9** |

- キャッシュが遠いと chunk_table、近いと chunk_pull が速く、チャンク数が増えると差が広がる
  （4 チャンクでは s1 で 0.2 ms 差、10 チャンクでは 0.8 ms 差）
- MCD ではよく要求されるコンテンツが Consumer の近くに来るので、一番多い状況では chunk_pull が速い
- chunk_pull は recirculate を使わないので移植しやすい。失われたチャンクだけを要求し直せ、
  off-path や複数 Consumer への対応もしやすい
- 既存の ICN（NDN）もセグメントごとに Interest を出す方式

### chunk_table は今の状態で止める

先行研究の再評価と、方式の比較・選択の根拠として研究に残す。今後は手を入れない。
研究の中では次のように位置づける:

> 先行研究の、1 つの Interest で全チャンクを返す方式（push 型）を修正して E2E で動かし、
> チャンクごとに要求する方式（pull 型）と比べた。push 型はキャッシュが遠い場合に有利だが、
> MCD でキャッシュが Consumer の近くに来た後は pull 型の方が速く、移植のしやすさや今後の拡張も考えて
> pull 型を採用した。

### FIB は「名前のプレフィックス → 出力ポート」

全部のスイッチが IWP の間は、次の IWP の番号を引いても結局ポートに変換するだけなので、直接ポートを引く。
次の IWP の番号を引く形（FIB → NMT）は (4) IP 上での動作から。

## 4. 今後の実装の順番

### (1) コンテンツ名

**方式: 階層ごとのハッシュ**

ホスト（Consumer / Producer）が名前を階層ごとにハッシュにし、固定長のフィールドとしてヘッダに載せる。
スイッチは文字列を扱わない。

```
例: /univ/lab/video/1
  name0  hash("univ")
  name1  hash("lab")
  name2  hash("video")
  name3  hash("1")       ← 階層が上限より少なければ 0 で埋める
  chunk_id
```

ほかの方法と比べてこれを選んだ理由:

| | 階層ごとのハッシュ | 文字列をそのまま固定長に詰める | 番号を割り当てる |
|---|---|---|---|
| 管理する仕組み | 不要 | 不要 | 必要（DNS のような名前 → 番号の仕組み） |
| 長い名前 | 扱える | 扱えない | 扱える |
| 最長プレフィックス一致 | できる | できる | できる |
| 衝突 | 起こりうる | 起きない | 起きない |

名前全体を 1 つのハッシュにすると階層の区切りが消え、FIB でプレフィックスをまとめられなくなるので、階層ごとにする。

**衝突への対策**

- 衝突が問題になるのは同じ親の下の名前どうしだけ（キーに親の階層のハッシュも含まれるため）
- 32 bit の場合、同じ親の下に名前が n 個あると、どれか 2 つが衝突する確率は約 n² ÷ (2 × 2³²)
  （1,000 個で約 0.01 %、10,000 個で約 1 %）
- Producer が公開前に、自分の名前どうしで衝突していないか確かめる（同じ親の下の名前はふつう同じ Producer が管理する）
- 必要なら、数が多くなりやすい最後の階層に多くのビットを割り当てる
- わざと衝突させる攻撃（偽のコンテンツをキャッシュに入れさせる）は範囲外とする。
  NDN は Data の署名で防いでいる

**決めること**

- 階層の数の上限と、各階層のビット数（全部同じか、最後の階層を長くするか）
- 全体の長さ: 128 bit にするか、(4) の方式 B も考えて 80 bit 程度に収めるか
- Data に元の名前の文字列を載せるか（Consumer が要求した名前と一致するか確かめる用）

### (2) FIB

```
表 fib
  キー:     名前（固定長）  最長プレフィックス一致（階層の区切り単位）
  動作:     forward(port)
  一致なし: デフォルト経路
```

- 表に置く。表はパケットごとに検索するための仕組みで、最長プレフィックス一致ができるのは表だけ。
  表に書き込めるのは外のプログラム（コントロールプレーン）だけだが、FIB は書き換えが少ないので問題ない
- 今の Interest の転送（送信元 MAC アドレスをキーにした表）を置き換える
- 中身は、実験ではトポロジ（`topology.json`）と Producer のプレフィックスの対応から経路を計算して書き込む
  簡単なプログラム（または静的な設定）で入れる。ルーティングは研究の範囲外
- Producer が複数あるトポロジや木構造のトポロジを組めるようになる
- (4) では表のキーはそのままで、動作を「次の IWP の番号を決める」に変え、NMT（IWP → ポート）を引く段を足す

### (1)(2) と同時に: register のインデックスの管理

PIT とキャッシュはパケットの処理中に書き込むので、表ではなく register に置く。
インデックスを `content_id × 10 + chunk_id` から、名前のハッシュに変える（ハッシュテーブル）。

```
index = hash(名前, chunk_id) mod N      （P4 の hash() で計算）

content_cache[index]  … チャンクのデータ
cache_tag[index]      … そこに入っている名前 + chunk_id
ヒットの判定: cache_tag[index] == 今の Interest の名前 のときだけ
```

| | 衝突したとき | 理由 |
|---|---|---|
| キャッシュ | 新しい方で上書きする | 消えても Producer から取り直せる。自然にキャッシュの置き換えになる |
| PIT | 上書きしない | 上書きすると前の要求の Data の戻り先がわからなくなる。候補を 2 つにし（ハッシュ関数を 2 つ使う）、両方埋まっていれば Interest を捨てて Consumer に要求し直させる |

総チャンク数のようにコンテンツ単位の情報は、chunk_id を含めない名前だけのハッシュをインデックスにする。

**決めること**: キャッシュと PIT の register の大きさ、PIT の候補の数

### (2)〜(3) の間: 基礎

(3) の評価（多数のコンテンツ、複数の Consumer）に必要:

- 複数の Consumer に対応した PIT（ポートをビットで持つ + マルチキャスト）
- PIT の記録の期限
- 重複の検出（nonce を入れるか）
- キャッシュの置き換え（ハッシュの上書きで最低限は実現できる。LRU などにするか）
- 1 コンテンツあたりのチャンク数の上限の見直し（今は 10 チャンク = 2.5 KB まで）
  - 64 チャンク程度までは BMv2 の待ち行列（既定 64 パケット）の範囲で試せる。
    それ以上は同時に出す Interest の数を絞る仕組みや、失われたチャンクを要求し直す仕組みが必要

### (3) off-path キャッシング

- ECST（近くの IWP がどのコンテンツを持っているか）と、その通知の仕組みを作る
- Interest を受け取ったら、LCST（自分のキャッシュ）→ ECST → FIB の順に見る
- ECST にも IWP の番号ではなくポートを記録する案: 「この名前のキャッシュを持っている」という通知は
  その IWP の方向から届くので、届いたポートを記録すれば、その方向に送ればキャッシュに届く。
  (4) までは IWP の番号なしで済む
- **一番の課題**: MCD ではキャッシュが要求のたびに移動するので、通知した情報がすぐ古くなる。次を決める
  - 通知のタイミング（キャッシュが移動したとき、一定時間ごと、など）
  - 通知を受け取る範囲（何ホップ先まで）
  - ECST にしたがって転送した先にキャッシュがなかったときの扱い（FIB で Producer 方向へ転送し直す、など）
- ここをどう解決するかが研究の工夫（新規性）になる

### (4) IP 上での動作

途中に通常の IP ルータがあっても通信できるようにする。2 つの方式から選ぶ（または両方作って比べる）。

| | 方式 A（`設計メモ.txt`） | 方式 B（hICN 寄り） |
|---|---|---|
| 名前の置き場所 | IP の上に載せる ICN ヘッダ | IPv6 の宛先アドレス（名前用に確保した範囲に、名前のハッシュを入れる） |
| 普通の IP ルータの扱い | 次の IWP の IP アドレス宛てにカプセル化する。IWP の番号から IP アドレスを引く NRS が必要 | 名前を宛先アドレスとしてそのまま転送する |
| 経路の広告 | ICN 用の仕組みが必要 | 既存の IP のルーティング（OSPF、BGP）を使える |
| off-path キャッシング | 両立する（キャッシュを持つ IWP 宛てにカプセル化する） | 組み合わせにくい（宛先が名前なので IP ルータは Producer 方向にしか送らない。SRv6 などが必要） |
| 使える IP | IPv4 / IPv6 | IPv6 のみ |
| hICN との違い | 説明しやすい | ほぼ同じになる |

- Data は Consumer の IP アドレス宛てに送る（両方式とも。hICN も同じ）。
  そのため同じ Data を待つ複数の Consumer にまとめて配れない（`設計メモ.txt` の欠点。全部が IWP になれば解消）
- FIB → NMT の 2 段階、IWP の番号はここから
- 経路上の IWP の割合を変えた評価で、「導入の壁を下げる」を示す

## 5. FIB の設定（実環境での説明）

研究ではルーティングは範囲外とし、実験は簡単なプログラムで済ませる。論文では次のように説明する。

- **役割分担**: コントロールプレーンが扱うのは FIB だけ（変わるのは Producer の追加・削除やリンクの故障のとき）。
  PIT、キャッシュ、ECST の通知のようにパケットやコンテンツごとに変わる情報は、スイッチの中や IWP どうしで完結する
- **設定の方法は 2 つ**

  | | 中央のコントローラ | スイッチどうしで伝えあう（分散型） |
  |---|---|---|
  | FIB を書くのは | 外の 1 台のコントローラ（P4Runtime で書き込む） | 各スイッチの横で動く小さなプログラム |
  | 道順の決め方 | トポロジの地図から計算する | 届いた広告から決める（距離ベクトル型）、または全員が地図を持って計算する（リンクステート型） |
  | 作りやすさ | 作りやすい | 大変 |
  | 止まったとき | コントローラが止まると更新できない | 一部が止まっても動く |
  | 範囲 | 1 つの組織の中 | 組織をまたげる |
  | 例 | SDN | IP の RIP / OSPF / BGP、NDN の NLSR（リンクステート型） |

- **実環境**: IP と同じく、組織の中は中央のコントローラか分散型、組織の間は分散型の二段構え
- **NLSR を使う場合**: この研究のパケットは NDN 形式ではないので、NLSR をスイッチどうしでそのまま動かすことはできない。
  各スイッチの横で NFD + NLSR を動かし（NLSR どうしは IP でやりとりする）、
  その結果の FIB を、名前を階層ごとにハッシュにしてポート番号に直し、P4 の FIB に書き込む形が考えられる
- **(4) の方式 B なら**、既存の IP のルーティングで名前のプレフィックスを広告できる
- **どの方法でも残る問題**: 名前のプレフィックスの数は IP のアドレスのプレフィックスよりずっと多くなりうる。
  階層の名前でまとめられることが、FIB を小さくする鍵になる。実機の表の行数には上限（数万〜数十万）がある
- **範囲外とすること**: 複数の経路（1 つのプレフィックスに複数のポート）、登録の正しさの確認（NDN は署名を使う）

## 6. 評価の方針

### 主張と評価を対応させる

| 主張 | 評価 |
|---|---|
| キャッシュ配置の工夫に効果がある | off-path あり／なしや、複数の配置方式（LCE、LCD、MCD など）を同じ枠組みで比べる |
| 配置を柔軟に変えられる | 方式を切り替える手間の小ささを示す |
| 導入の壁が下がる | (4) の後で、経路上の IWP の割合を変えて効果を見る |

### 条件を現実に近づける

今は「Consumer 1 台、コンテンツ 1 つ、同じものを連続で要求」なので、キャッシュが効くのは当然。今後は:

- 多数のコンテンツ、人気に偏りのある要求（Zipf 分布）
- 有限のキャッシュ容量
- 複数の Consumer、木構造のトポロジ

### 指標

取得時間に加えて、次を出す。これらは BMv2 の性能に左右されない。

- キャッシュのヒット率
- Data が返ってくるまでのホップ数
- Producer に届いた要求の数
- 各リンクを流れたパケットの数

### 実験の進め方

- Docker で回す → スクリプトが結果を出す → グラフもスクリプトで作る、を続ける。数値を手で書き写さない
- 比べる方式は交互に回す（時間による環境の変化を両方に散らす）
- 性能を測るときは BMv2 のデバッグログを止める（比べる方式すべてに同じ条件で）
- 環境が違う結果どうし（Docker と VirtualBox など）は直接比べない

## 7. まだ決めていないこと

- **(1) の名前**: 階層の数とビットの割り当て、全体の長さ（128 bit か 80 bit 程度か）、Data に元の名前を載せるか
- **(1)(2) の register**: キャッシュと PIT の大きさ、PIT の候補の数
- **(4) の方式**: A、B、または両方を作って比べるか
- **コンテンツ本体をどこに置くか**: 今はスイッチの register。
  BMv2 だけを前提にするか、ほかの環境（P4-DPDK、市販の P4 スイッチ + サーバ）を想定するか。
  実機の P4 スイッチはメモリが小さく、パケットの中身を読める深さにも上限があるので、
  スイッチは転送とキャッシュの判断、コンテンツ本体はつないだサーバ、という分担も考えられる。(4) の前までに決める
- **研究のスケジュール**: 締め切りや発表の予定に合わせて、どこまでやるかを決める
- **前の環境（VirtualBox）の結果がばらついた原因**: 今の `consumer_bench.py` と `run_compare_chunk_methods.py` を
  VirtualBox で回せば、原因が前の計測スクリプトか環境かを切り分けられる

## 8. 押さえておく関連研究

- **NDN.p4**: P4 で NDN の転送を実装した研究。名前の扱いの制限（階層の数や長さ）を引用する
- **NLSR**: NDN の分散型ルーティング（リンクステート型）
- **hICN**（Carofiglio ら "Hybrid Information-Centric Networking", ACM ICN 2019 / draft-muscariello-intarea-hicn）:
  名前を IPv6 アドレス（プレフィックス）+ セグメント番号（TCP ヘッダの欄を流用）で表し、
  IP ネットワーク上で ICN を動かす。(4) の方式 B と近く、違いの説明が必要
- **NetCache**: Tofino スイッチの中にデータをキャッシュする研究。スイッチの中にどれだけ置けるかの参考
- **Laoutaris らの LCD / MCD の論文**: 階層キャッシュの配置方式。配置方式を比べるときの基準
